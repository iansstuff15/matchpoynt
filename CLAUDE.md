# Matchpoynt
Matchpoynt is a multi-sport court session app for badminton, pickleball, tennis, padel, table tennis, volleyball and similar sports. It handles fair player queueing, court assignment, scores, fees and rankings for club nights and open play. It ships from one React codebase to two targets: the **website** (marketing pages, public rankings, sign-in, published session leaderboards) and a **desktop app** built with Tauri. Both are thin clients of one **API** (`server/`), which owns every rule. It began as a recreation of shuttleflow.ph. Nothing in the product, copy or config may assume a single sport.

- Tailwind CSS
- PNPM (workspace: root web app, `server/`, `shared/`, `test/`)

- Drizzle (`drizzle-orm`, `drizzle-kit`) for the database schema and migrations
- Zod for API input validation
- TanStack Query for data fetching in the web app
- GSAP (with `@gsap/react`) for JS-driven animation
- Docker
- Docker Compose

# Server-side Boundary (Mandatory)
- No API, auth, storage or business logic runs on the client. The web app and the desktop webview only render, collect input and call the Matchpoynt API. Everything else happens in `server/`.
- The client never imports `@supabase/supabase-js` or a Firebase SDK, never talks to Supabase or Firebase, never holds or reads a token, and never uploads straight to storage.
- "Business logic" includes queueing order, matchmaking, court assignment, score validation, deciding winners, leaderboards and rankings, fees, permissions and input validation. The client may shape form state (adding a court row to a draft), but whether that draft is valid is decided by the API.
- The client asks the server for derived data instead of computing it. The queue arrives ordered, `canStartMatch` arrives as a flag, and the leaderboard arrives ranked.
- Auth state lives in httpOnly, `SameSite=Lax` cookies set by the API. The client knows who is signed in only by calling `GET /api/auth/me`, and only while sign-in is on. Sign-in links point at `/api/auth/*`.
- Guest mode: with `FEATURE_WEB_SIGN_IN=false`, the API's `resolveUser` creates a guest (Firebase anonymous sign-in, `startGuest` in `utils/auth/session.ts`) on a browser's first write, so sessions still have an owner and RLS still applies. Reads never create guests. Guest data lives as long as the browser's cookies. This needs the Anonymous provider turned on in Firebase (Authentication > Sign-in method).
- The client shows server errors in an error banner (`components/feedback/ErrorBanner`), never in a toast or the console. See Feedback Requirements.
- New features start in the API: endpoint, rules and tests in `server/`, then a hook in `utils/hooks/` and the UI.

# Architechtural Requirements (Mandatory)
- git ignore and docker ignore should be based on this project.
- Functions should be handled inside `utils` directory and separated by concern i.e. database connections, business-logic, auth, etc. In the web app, `src/utils/` holds UI concerns only: `api/` (the fetch client), `hooks/`, `forms/`, `platform/`, `desktop/`, `theme/`, `seo/`, `time/`. Business logic, auth and database code live in `server/src/utils/` (`session/`, `supabase/`, `http/`, `validation/`).
- Use Typescript custom interface and type or `extend` existing ones whenver possible or a needed. have them inside `types` and `interfaces` directory. Types used by both the web app and the API (request and response bodies, sport rules) live in `shared/src/types` and `shared/src/interfaces`.
- Use `@apply` and `@layer` in tailwind css whenever writing css to make thing reusable.
- Build the UI from shadcn/ui components. Add them with the shadcn CLI through `pnpm ui:add <name>` into `components/ui`, then compose or extend them. The wrapper runs `pnpm dlx shadcn@latest add` and works around shadcn 4.22 registry items importing `cn` from a bare `"cn"`. Do not hand-roll a primitive that shadcn already provides (button, badge, card, dialog, sheet, tabs, accordion, carousel, table, skeleton, etc.).
- Files in `components/ui` belong to the shadcn CLI. They are exempt from the one-export rule below. Brand changes go in as `cva` variants inside those files so `shadcn diff` stays readable. Every other component wraps them.
- `components.json` aliases must point into this structure: `utils` → `@/utils/cn`, `lib` → `@/utils`, `hooks` → `@/utils/hooks`, `ui` → `@/components/ui`, `components` → `@/components`. There is no `lib` directory.
- Have animations in the `animations` directory. Simple, state-driven motion (a pulse, a fade) is CSS keyframes registered as Tailwind `--animate-*` theme tokens. Everything JS-driven uses GSAP:
  - Each GSAP animation is a function in `animations/` that takes elements and returns a cleanup function (e.g. `splashTimeline`, `heroIntro`, `waveHeading`, `revealSection`, `marquee`, `landingSection`).
  - GSAP and its plugins (ScrollTrigger, SplitText) are registered once in `animations/registerGsap.ts`; import `gsap` from there.
  - Components run animations through `useMotion(ref, fn)` (`animations/useMotion.ts`, built on `useGSAP`), never with raw effects, so they are cleaned up on unmount.
  - Timings, eases and distances come from `config/motion.ts` (`motion.gsap`), never literals in the function.
  - Mark what moves with data attributes instead of extra refs: `[data-wave]` for a heading that rides in letter by letter, `[data-reveal]` for items that rise in order.
  - Split text with `SplitText` and `aria: 'auto'`, so screen readers still read the heading as one phrase.
  - Don't tween theme colours: they are `oklch`, which GSAP can't interpolate. Fade or move instead.
- Every animation must respect `prefers-reduced-motion`: `useMotion` skips GSAP entirely, the splash doesn't play, and CSS animations are cut to a single instant frame.
- Colors, fonts, font weights and sizes, and motion timings should be handled inside `config` directory. shadcn's semantic tokens (`--background`, `--primary`, `--card`, `--border`, …) are generated from `config/theme.ts`, never hand-edited in CSS.
- Feature toggles for web and desktop are environment variables on the API (`FEATURE_WEB_*`, `FEATURE_DESKTOP_*`). Their names and defaults live in `shared/src/config/features.ts`. The API parses them in `server/src/config/features.ts`, rejects malformed values at startup, and serves them at `GET /api/config`. Clients read them with `useFeatures()`.
- A toggle controls every surface of its feature, on both sides:
  - Web app: routes, navigation, buttons, cards, menus.
  - API: routes (`requireFeature`) and response fields (e.g. `publicUrl` is `null` while publishing is off).
  - Anything that depends on a switched-off feature must keep working in a reduced form, never ask for the missing feature. Example: with sign-in off, the board runs in guest mode instead of showing a sign-in prompt.
  - When adding a toggle, list every place it shows up and gate each one.
- Toggles fail closed. The web app renders no routes until `/api/config` first answers. If it can't be reached, every feature counts as off (`featuresOff`) and API-backed screens say the API is unreachable. A default is never used to switch a feature on.
- If API calls are done use nginx proxy to prevent CORS policy errors. The web app calls same-origin `/api`, which nginx forwards to the API container (Vite's dev server proxies `/api` to `localhost:8787`).
- queries should be done via ORM, have queries in `queries` directory. In practice that's `server/src/queries/`, using `@supabase/supabase-js` as the signed-in user. The web app has no `queries/`.
- secrets or API keys should be expected to be inside and handled by a .env file or its equivalent. `.env` is read only by the API and by migrations. Nothing reaches the web or desktop bundle: there are no `VITE_` variables.
- Whenever a block of elements gets created repeatedly have it as a component under `components` directory.
- A set of components being called by a parent component is a valid component i.e. Header, Footer, and Sections.
- Component files should only export one element. If exports are logically related create subdirectory/ies inside `components`
- Whenever data is being fetched for a component use skeleton components for them (shadcn `Skeleton`). A skeleton mirrors the loaded layout: same grid, the same `Card`/`Table` frames, column set, row and item counts, and element sizes, so nothing jumps when data arrives. Build it from the real container components with `Skeleton` blocks inside, and keep it next to the component it stands in for (`CourtCardSkeleton` beside `CourtCard`). The startup skeleton (`AppLoading`) matches the route being opened.
- Buttons, and navigations should have icons by default unless stated to omit (use `lucide-react`, shadcn's icon library).
- Include navigation in the footer but omit the icons.
- Website should omit logs and toast whenever errors is produced by API calls, missing required config values, or secrets. Errors get an error banner instead (see Feedback Requirements).
- Components should have search engine friendly labels and descriptions.
- Docker container should not have any secrets embedded inside it (it will be added on runtime).
- Docker container should be multi-stage.
- Building of the application, installs, or its equivalent should be handled on build stage.
- nginx, react and API builds should be on separate docker containers.
- alpine, slim, or its equivalent should be used if its available as base image.
- last user should not be root name it base on the project.
- container filesystem should be read-only.
- do not create files inside container during run-time, if files are needed it should either be copied from the project into the container during build stage or created during build stage.
- any files that is needed to be written should be inside a volume based on the host machine i.e. logs.
- use docker network to communicate between containers.
- Vercel is a second delivery path for the web app and the API (`vercel.json`, Vercel Services): service `app` (the Vite build, every unknown path falls back to `index.html`) and service `server` (framework `hono`, entrypoint `src/vercel.ts`, `outputDirectory` `dist/vercel`: Vercel deploys that folder as the function, so the build makes it self-contained with the bundle as `index.js`, its own `wasm/` and a `package.json` marking it ESM). `pnpm deploy:vercel` (`scripts/deploy-vercel.mjs`) copies the API's secrets from `.env`, checks the required variables, deploys and calls `/api/config`. `.vercelignore` keeps `.env`, `src-tauri/`, installs and build output out of the upload. The top-level rewrites send `/api/*` to `server` with the path unchanged and everything else to `app`, so the web app still calls same-origin `/api`. The security headers and CSP in `docker/proxy/nginx.conf` are repeated in `vercel.json`'s top-level `headers`; change both together. No service calls another, so there are no bindings. The desktop app is not a Vercel service.
- docker compose should have `.local` and `.prod`.

# Session Board Requirements (Mandatory)
- Queueing is a per-session setting (`rules.queueing`), switchable from the board header and from Session settings:
  - **automatic:** the matchmaking algorithm picks who plays next, and auto-fill may start matches;
  - **manual:** the Queue Master drags every player onto a court; nothing is picked, and auto-fill is off.
- In both modes players can be dragged from the queue onto a side of an open court, between courts, and back to the queue. Placed players are stored on the court (`session_courts.lineup`) and leave the fair queue.
- Starting a match keeps placed players on their sides. In automatic mode the algorithm fills the open places; in manual mode the lineup must be full. Auto-fill never touches a court someone is arranging.
- The API decides every move (`assignPlayer`, `unassignPlayer`, `startBlockedReason` in `utils/session/engine.ts`) and says why a court can't start. The board shows that reason under the button. The web app only previews a drag optimistically (`utils/forms/lineupPreview.ts`) until the API answers, and reloads the board if the API refuses.
- Board changes run one at a time (one mutation scope), so each request carries the version the previous one produced.
- Every playing court shows its elapsed time. When the session's match time limit is on (Session settings > Rules), it also shows a countdown with a progress bar:
  - it turns to a warning for the last `board.timerWarningMs` (`config/board.ts`);
  - after the limit it shows "Over by m:ss", and a toast announces the court going over once.
  The API sends each match's `endsAt`, so the browser never works out the deadline itself. It also sends `serverTime`, and timers add the difference to the device clock, so a device with a wrong clock still shows the right times. Each playing court runs one clock; open courts don't tick.
- Every app page has a breadcrumb trail at the top, on the sidebar-coloured frame above the light page panel, in the sidebar's text colours (`AppBreadcrumbs`, shadcn Breadcrumb, built by `useBreadcrumbs` from what the page already loaded): e.g. "Session board / Tuesday night", "Clubs / <club> / Members". Large display type, earlier steps dimmed and linked, the page on screen bold, "/" between, like the reference design; back links such as "← All clubs" sit under it.
- The app shell is exactly the screen's height (`AppLayout`). On the session page the main column scrolls on its own. While a session runs, the queue is a full-height panel on the right with a small margin (`.session-page-split`, `.session-queue-panel` in `index.css`); below `lg` it stacks under the board. Only the queue's player list scrolls (shadcn `ScrollArea`, `.board-queue`); its header stays put. The board and the queue panel share one `BoardDnd`.
- Every queued player shows how long they've waited for their next game (`WaitTime`, an hourglass and m:ss), in the next-match groups and the waiting list. The API sends `waitingSince` on each `PlayerView` (when they joined the queue: on check-in, or when their last match finished; `null` on court or not checked in). The panel runs one clock for all of them, corrected by `serverTime` like court timers, and waits over `board.longWaitMs` (20 min) turn to the warning colour.
- With automatic queueing the queue shows who plays next and against whom. The API sends `upNext`, from `upcomingMatches` in `engine.ts`: the session's matchmaking run over the queue, exactly as starting an empty court would pick and split it. The panel shows those matches, then the players still waiting for a full group. With manual queueing it's the plain call order.
- An open court can be removed from its card (trash button, confirmed first, `DELETE /api/sessions/:id/courts/:courtId`, `removeCourt`): never with a match on (playing courts show no button), never the last court or a running tournament's last court. The API sends each court's `removeBlockedReason`, shown as the disabled button's tooltip. Players placed on it go back to the queue; `save_session` deletes courts left out of the save.
- Above the courts, `BoardTools` holds adding a player (`AddPlayerForm`, compact) and "Add court" on one row, in a collapsible section (shadcn Collapsible; this browser remembers it open or closed, `boardTools` in `utils/platform/remember.ts`). "Add court": The API names the court (the first free "Court N"), enforces `maxCourts` (`canAddCourt` / `addCourtBlockedReason`), and auto-fills it.
- A Queue Master can run several sessions at once. Every session has its own page, `/app/<session id>`: its board while it runs (`GET /api/sessions/:id`), then "Session ended" with its leaderboard (`GET /api/sessions/:id/ended`), so the link keeps working after newer sessions. `/app` itself opens no session: it lists them (`SessionsOverview`): the sessions set up and running (`RunningSessionCard`, from `GET /api/sessions/active`, each opening its board) and every finished one, newest first (`PastSessionCard`, `GET /api/sessions/ended`, a page at a time with "Show older sessions"). It never shows a session's leaderboard, results or invoices; those are on each session's own page. Setup never opens on its own: with no sessions at all the board shows its empty state (`SessionEmptyState`, "Set up session"), and "New session" (`/app?new=1` from the sidebar) starts another without ending any. `?new=1` is handled once per visit (a flag in `SessionPage`): clearing it changes the address only after that render.
- There is no Past sessions page: finished sessions are listed on the session board (`/app`, "Previous sessions" in `SessionsOverview`), every one, newest first, a page at a time (`GET /api/sessions/ended?before=<ended_at>`, `sessionHistory.pageSize`, "Show older sessions"), each card (`PastSessionCard`) opening the session's page with its final leaderboard or deleting it. Finishing a session refreshes the list. Old `/app/past` links redirect to `/app`.
- `SessionSwitcher` lists the running sessions, "New session" and "All sessions" (the session board). It sits on the board's header and at the top of the sidebar's **You** group (`SidebarSwitcher`).
- The app sidebar has two named groups (`appNavigation` in `config/navigation.ts`, `switcher` on `AppNavGroup`): **You** (the session switcher, then Session board, Find clubs and Your profile) and **Club**, named after the selected club (the club switcher, then the club's pages and All clubs). Each group is a `group` landmark named by its label. The footer has "What's new" and the version. Board queries are per session (`queryKeys.session(id)`), and changes run one at a time per session.
- Drag and drop uses `@dnd-kit/core` with mouse, touch (press and hold) and keyboard sensors, plus screen-reader announcements. Auto-scroll while dragging only kicks in right at the edge (`board.dragAutoScrollEdge`), so picking up a player at the bottom of the queue doesn't move the board. Every placed player also has a button to send them back to the queue without dragging.
- Courts are plain cards (`CourtCard`): the two sides as panels with "vs" between (`.court-matchup`, `.court-side` in `index.css`), no drawn court. Every card in a session is the same fixed height, open or playing: player rows are `.court-row`, the matchup is centred vertically in the card's middle (`.court-body`), and the footer sits at the bottom with one fixed-height slot (`.court-footer-slot`): a playing court's countdown above "Finish match" (`.court-timer`), or an open court's start-blocked reason, up to two lines, below its button (`.court-reason`).
- Restarting (`restartMatch`, `restartSession` in `engine.ts`):
  - A playing court has a "Restart match" icon button beside "Finish match" (confirmed first, `POST /api/sessions/:id/courts/:courtId/restart`): the same match replays with the same players on the same sides, the clock back to 0:00 and the score back to 0–0 (the score dialog is keyed by match and start time), nothing recorded. `save_session` saves a match's `started_at` (0018) so the new clock sticks.
  - A playing court also has "Cancel match" (`cancelMatch`, confirmed first, `POST /api/sessions/:id/courts/:courtId/cancel`): no result is recorded, the players go back to the queue where they were (starting a match doesn't move anyone in it), and the court opens without auto-fill refilling it straight away. A tournament match goes back to waiting for a court. Saves never delete matches, so `cancel_match` (security invoker, 0019) deletes that in-progress match and calls `save_session` in one transaction.
  - The board header has "Start over" (`StartOverButton`, confirmed first, `POST /api/sessions/:id/restart`): every result and match on court is cleared and the tournament dropped; courts, settings and players stay, check-ins included; everyone goes back to the queue in arrival order with no games played, and auto-fill starts again. Saves never delete matches, so `restart_session` (security invoker) deletes the session's matches and calls `save_session` in one transaction, with its version check.
- Taking a break: a checked-in player off court can sit out (`breakSince` on the player, `session_players.break_since`, saved by `save_session` 0048). The engine leaves them out of the queue, lineups, auto-fill and up next (`isOnBreak`, `onBreak`, `breakBlockedReason`: not on court, not still in the tournament; `setPlayerBreak` takes them off a court they were placed on, and coming back queues them from now at their rotation). The board's queue gives each waiting player a break button and lists "On a break" with Back (`OnBreakList`, `PUT /api/sessions/:id/players/:playerId/break`, the view's `onBreak`). Players start and end their own from their live view (`PlayerStatusCard`, `POST /api/play/:sessionId/break`, status `on_break`, `breakSince`/`breakBlockedReason` on `PlayerLiveMe`) through the `security definer` function `set_player_break`, which matches them by roster name and bumps the version; a club's running board polls every `board.clubSessionPollMs` so it shows up.
- Deleting a session is separate from finishing it: "Delete session" (`DeleteSessionButton`, confirmed first, `DELETE /api/sessions/:id`) removes a running or finished session for good (courts, players and matches cascade; published links stop working). It's on the running board's header, the finished session's page and each previous session's card on the session board. `useDeleteSession` drops it from the cached session lists at once (so `/app` never reopens it) and forgets it as the last opened session.
- The board header has a "Finish session" button (`FinishSessionButton`, confirmed first). It ends the session through `POST /api/sessions/:id/end`; finished results stay on the leaderboard and check-in closes. A session can't end while a match is on court: the API refuses (`endBlockedReason` in `engine.ts`), and the view's `canEnd`/`endBlockedReason` disable the button with the reason.
- Check-in: only checked-in players are matched, auto-filled or placed on courts.
  - Roster players from setup start not checked in, unless "Already checked in" is ticked for them (`MemberSetup.checkedIn`; the box starts unticked in setup and resets after each player). Players added from the board are checked in unless that box is unticked (`AddPlayerInput.checkedIn`, default true). In Session settings, ticking a waiting player checks them in; a recorded check-in can't be undone there.
  - The QR sits behind the "Check-in QR" button (`components/session/checkin/CheckInButton`), opened in a dialog with the check-in count. Its link (`/check-in/<128-bit slug>`) is made on first open (`POST /api/sessions/:id/check-in`) and then kept, so a printed QR keeps working.
  - Scanning opens `CheckInPage`: the player picks their name and checks in, signed out, through `/api/public/check-in/:slug` and the `security definer` functions `public_check_in_roster` / `public_check_in`. The function only records `checked_in_at` and doesn't bump the version.
  - The engine's `settleCheckIns` puts recorded check-ins into the queue in arrival order, at the late-joiner rotation, on every load. `save_session` never clears a recorded `checked_in_at`.
  - The queue card lists players still to check in under the queue, each with a "Check in" button for the Queue Master. While anyone is still to check in, the board polls (`board.checkInPollMs`) and toasts new check-ins.

# Club Manager Requirements (Mandatory)
- An account can run several clubs. "Clubs" in the sidebar (and site navigation) opens `/clubs` (`ClubsPage`), a picker styled like a streaming service's profile screen: big round club avatars (`ClubPickerTile`) on a deep stage, "Add club", and an "Edit clubs" mode (`?edit=1`; `?new=1` opens "Add club"). Each club's pages share `ClubLayout` (`src/pages/club/`), which loads the club once, remembers it as the one opened last, holds its actions and settings dialog, and hands them to the page (`useClubPage`). The pages are sidebar links in the club's group (`clubPage` on `AppNavItem`, `clubPageHref`), and old `?tab=` links redirect to them. There is no "All clubs" back button on them (the sidebar and breadcrumbs have it):
  - **Dashboard** (`/clubs/<club id>`, `ClubDashboardPage`): the banner (`ClubHero`: cover and profile photos, clicked to view or change them, name and @handle, counts, "Finish setting up · N left" while anything is, and a Settings button); "Finish setting up" is a dialog (`ClubSetupDialog`): what the club is still missing, from the API's `setup` on `ClubView` (`clubSetup` in `server/src/utils/club/setup.ts`: handle, description, photos, colours, fee scheme, social links, members, a first session), each with the button that opens its settings group, its photo editor or its page. It opens by itself the first time a club's dashboard is shown in this browser (`setupShown` in `remember.ts`), and from the banner after that; defaults are fine ("Keep the defaults for now"); **Club info** (`ClubInfoCard`): name, description, colours, fee scheme, saved themes and counts, read only, with "Edit settings"; the club's sessions (`ClubSessionsCard`: next planned and latest run); and this month's money (`ClubMoneyCard`, while accounting is on).
  - **Sessions** (`/sessions`): planned sessions as cards (`PlannedSessionCard`) and the sessions the club has run (`ClubSessionCard`, linking to `/app` or `/app/<session id>`).
  - **Members** (`/members`): the roster (`MemberTable`), added and edited in `MemberDialog`.
  - **Badges** (`/badges`): the club's own badges (`ClubBadgesPanel`; see Club Badge Requirements).
  - **Feedback** (`/feedback`): the club's post-session feedback form and results (`ClubFeedbackPage`; see Club Feedback Requirements).
  - **Announcements** (`/announcements`): news for members (`ClubAnnouncementsPage`; see Club Announcement Requirements).
  - **Invoices**, **Expenses**, **Billers** and **Accounting** (`/invoices`, `/expenses`, `/billers`, `/accounting`): see Club Accounting Requirements.
  Other pages get a compact header (`ClubPageHeader`: avatar, name, settings button).
- Everything editable about a club is behind its settings button, in `ClubSettingsDialog`: a sidebar of groups (`clubSettingsGroups`, `config/clubSettings.ts`) and the group on screen: **General** (`ClubInfoForm`: name, @handle and description), **Social links** (`SocialLinksEditor`), **Appearance** (`ClubAppearanceSettings`), **Fees** (`ClubFeeSettings`, while fees are on), **Payment QR codes** (`ClubPaymentQrSettings`, while fees are on) and **Delete club** (`ClubDeleteSettings`). Photos aren't in it: they change by clicking them on the dashboard.
- Every club has a unique **@handle** (`clubs.handle`, lower case without the "@": letters, digits, dots and underscores, 3 to 30, starting and ending with a letter or digit; `handleRules`, `handleProblem`/`normalizeHandle` in `server/src/utils/social/handles.ts`; a unique index backs it, and a clash maps to a field error). `HandleField` checks it as it's typed (`useNameCheck`, `GET /api/clubs/handle-check?value=&club=`, through the `security definer` function `club_handle_taken`, which only answers yes or no), and the create form's Next and Create stay disabled until it's free; the API checks again before creating or renaming. The handle is mandatory: a club without one (made before handles) gets `ClubHandleRequiredDialog` on every one of its pages (`ClubLayout`), which can't be closed (no close button, Escape and outside clicks do nothing) until a free handle is saved (`saveInfo`; it starts from the name, `handleFromName` in `utils/forms/handle.ts`). "Finish setting up" waits until then. The handle shows in the banner, the page header and Club info.
- Clubs and people can list **social links** (`social_links` columns, `SocialLink`, `socialPlatforms` in `shared/src/config/social.ts`: Facebook, Instagram, X, TikTok, YouTube, Threads, LinkedIn, Discord, Strava or any website; up to `socialLimits.maxLinks`). `cleanSocialLinks` (`server/src/utils/social/links.ts`) adds https, refuses anything that isn't a web address or isn't on its platform's site, and repeats (`PUT /api/clubs/:id/social`, `PUT /api/profile/social`). They're edited in `SocialLinksEditor` and shown by `SocialLinksList`, each with its platform's logo (`SocialIcon`: one SVG path per platform in `config/socialIcons.ts` from `simple-icons` (CC0), drawn in `currentColor` so it reads on every club theme; LinkedIn isn't in Simple Icons, so its "in" mark is drawn there; a website gets lucide's globe).
- Creating a club is step by step (`CreateClubDialog`, steps in `config/createClub.ts`): **Details** (name, @handle suggested from the name until typed, description), **Colours** (`ThemePresets`, `ThemeColorFields`), **Fees** (`FeeSchemeFields`, while fees are on) and **Review** (`CreateClubReview`, marking what keeps its default). Colours and Fees have "Use default". `POST /api/clubs` takes the info with `theme` and `fee` (`createClubSchema`; `null` keeps the default) and creates the club with them in one request; the API's complaints jump to the step they belong to. It then opens the new club's dashboard, whose checklist asks for the rest.
- Members are a named roster: a name, optional contact and a skill tier per sport (`club_members`, `club_member_sports`). A member can be invited by email (`InviteMemberDialog`, `POST /api/clubs/:id/members/:memberId/invite`): the API stores an invite with an unguessable token (`club_invites`) and emails a sign-in link of its own (`sendInviteEmail`: Firebase's `EMAIL_SIGNIN` code, which creates the account if there is none) that returns through `/api/auth/action` to `/invite/<token>` (`InvitePage`). A new account fills in the sign-up form there with its own password (`SignUpForm` mode `invite`, email fixed); an existing one just joins. `POST /api/invites/:token/accept` saves the profile and password, then `accept_club_invite` (security definer, only for the email it was sent to, and only once Firebase has confirmed the caller owns it: `email_verified` on the token) links the account to the member (`club_members.user_id`). The members table shows Joined / Invited, with resend and cancel. Invites need `FEATURE_WEB_SIGN_IN` and `FEATURE_WEB_SIGN_IN_EMAIL`.
- Members have a **role** (`club_members.role`, `clubMemberRoles` in `shared/src/config/club.ts`: member, captain, coach, Queue Master, manager), picked in `MemberDialog` and saved with the member (`ClubMemberInput.role`; left out, a new member is a `member` and an edit keeps theirs). The members table badges anything other than member. Roles are titles: they don't grant management rights (RLS still lets only the owner manage the club). Players see the club's team (everyone with another role) and their own role on its page (`ClubTeamCard`, `team`/`myRole` on `PlayerClubPageView`, through the `security definer` function `club_team`).
- Club management is for accounts that run sessions. Player-only accounts (`profiles.role = 'player'`) are refused by the API (`requireClubManager` on `/api/clubs` and `/api/accounting`, `manageClubsBlockedReason` in `server/src/utils/profile/rules.ts`, with how to change it), and `me` says so (`canManageClubs` and `role` on `CurrentUser`). The web app reads it with `useCanManageClubs` (guests with sign-in off can): nav items and groups marked `clubManager` are hidden (the Club group, Clubs, the Clubs tab), club lists aren't fetched, the Fees step offers no club fees, and `RequireClubManager` sends `/clubs` and every club page to Find clubs (or the board while the directory is off).
- Player-only accounts don't run sessions either: the API refuses them the session board, its history, session invoices and member suggestions (`requireSessionRunner`, `runSessionsBlockedReason`), and `me` says so (`canRunSessions`). The web app (`useCanRunSessions`) hides nav items marked `sessionRunner` (Session board, the Board tab) and the session switcher, and `RequireSessionRunner` sends `/app` and every page under it to their home in the app (`useAppHome`: Playing now, else Find clubs, else their profile), where the logo and the signed-in home page redirect take them too.
- Club photos can be aligned: in `PhotoEditDialog` (from the viewer's Edit, straight away when there's no photo yet, or the setup checklist) `PhotoAligner` drags the photo (or arrow keys, Shift for bigger steps) and zooms it (`photoPositions` in `shared/src/config/club.ts`). The API checks and saves `{ x, y, zoom }` (`cleanPosition` in `server/src/utils/club/appearance.ts`, `PUT /api/clubs/:id/:kind/position`, columns `avatar_position`/`cover_position`); a new upload starts centred. Everywhere a club photo shows it's drawn by `PositionedPhoto` (or `ClubAvatar` with `position`) at that point and zoom.
- A club has its own colours (Appearance in the club settings, `ClubAppearanceSettings`): an accent (buttons, highlights, the selected sidebar item), a sidebar colour and a page colour (the centre panel), from `clubThemePresets`, the club's saved themes or any colour. The API checks them and works out readable text and the sidebar's shades (`cleanTheme`, `themeOf`: WCAG contrast; `PUT /api/clubs/:id/theme`, column `theme`), sending `theme` on `ClubSummary`. From the page colour alone it works out the panel's text, cards (and menus and dialogs), muted fills and text, and borders (`pageShades`), so a dark page turns everything on it around and every text colour reaches 4.5:1 on what it sits on; colours saved before the page existed read as Matchpoynt's own (`colorsOf`).
- Custom colours can be saved as named themes (`POST /api/clubs/:id/themes` with `{ name, colors }`, `DELETE /api/clubs/:id/themes/:themeId`; `withSavedTheme`: a name no other saved theme has, at least one colour, up to `clubThemeLimits.maxSaved`; column `clubs.saved_themes`, sent as `savedThemes` on `ClubSummary`). They're listed beside the presets (`ThemeSwatch` shows sidebar, page and accent) to pick again, and each can be deleted. `useClubTheme` (in `AppLayout`) sets those as the theme's CSS variables on the page root: a session's own club on its page (`clubId` on `SessionView` and `EndedSessionView`), the club on screen in the club manager, otherwise the club picked in the sidebar; Matchpoynt's colours otherwise.
- Clicking the club's profile or cover photo on its page opens `PhotoViewerDialog` (zoom with buttons or the mouse wheel, steps in `photoZoom` in `config/club.ts`) with an Edit button that opens `PhotoEditDialog`; with no photo yet, the click opens `PhotoEditDialog` straight away.
- `ClubSwitcher` (sidebar) switches clubs like switching profiles: round avatars and names, "Add club", "Edit clubs", "All clubs". It shows the club on screen or the one opened last.
- Typing a player's name (board's add-player form and session setup) suggests up to 5 club members (`MemberNameField`, shadcn Command in a Popover; `GET /api/members/suggestions`), matched by name, or by the start of their email or @username. Each row (`PersonRow`) shows the photo, name, @username and email of a member linked to an account (`club_member_cards`, owner only). The API ranks them (`rankSuggestions` in `server/src/utils/club/suggest.ts`: the session's club first, then names starting with what's typed) and leaves out players already in the session or the draft. Picking one fills the name and, if set, their tier for the session's sport.
- Owners also invite people in the app: in `MemberDialog`, the name field (`PersonSearchField`) suggests up to 5 people on Matchpoynt by name, email or @username (`GET /api/people/search?q=&club=`, the `security definer` function `search_people`: never the caller or the club's members, LIKE wildcards stripped, at least 2 characters). Picking one sends `userId` with the member, and the API stores an app invite (`createAppInvite`: `club_invites` with `user_id`, no email). The person accepts or declines it on Find clubs (`MyInvitesCard`, `GET /api/directory/invites`, `POST /api/directory/invites/:id`, `respond_club_invite`), or by joining the club. The members table shows "Invited in app".
- Lists are paged, never loaded whole: the club picker (`useClubPages`, `pageSizes.clubs`, "Show more clubs"; the switchers keep the first page), the club's sessions (the first page in `ClubView`, then `GET /api/clubs/:id/sessions?before=`, "Show older sessions"), its invoices (`?offset=`, `pageSizes.clubInvoices`) and expenses (`?offset=`, `pageSizes.expenses`; the count and totals still cover every match). Sizes are in `shared/src/config/club.ts`.
- A planned session (`planned_sessions`) holds a title, an optional date, the session settings, courts and a roster of club member ids. `PlanSessionDialog` reuses the session setup steps plus a Details step and a member picker (`PlanMembersStep`); the steps are `planSteps` in `config/planSetup.ts`. Starting a plan (`POST /api/clubs/:id/plans/:planId/start`) builds the setup from the members' current names and tiers (`planToSetup` in `server/src/utils/club/rules.ts`; no tier for the sport means the sport's first tier), then `start_planned_session` saves the session, carries over the club, title and cover, and removes the plan in one transaction. The board then opens at `/app`.
- Sessions can have a cover photo, set on the plan. Cards with a cover show it as their background (`CoverCard`, `.cover-card` with a `scrim` overlay so text stays readable): club cards, planned and club session cards, and the "Session ended" card.
- Photos (club profile and cover, session covers) are uploaded to the API as multipart forms (`PUT .../avatar`, `.../cover`, `.../plans/:planId/cover`). The API checks the size (`clubImages` in `shared/src/config/club.ts`, 4 MB, under Vercel's 4.5 MB request limit) and the real type from the file's bytes (`sniffImage`), converts every photo to WebP (`toWebp` in `server/src/utils/image/webp.ts`: JPEGs turned upright from their EXIF orientation first, metadata such as GPS dropped, quality and a pixel limit in `server/src/config/images.ts`), then stores it in the `club-media` Storage bucket as the user, under `<owner id>/<club id>/<kind>-<uuid>.<ext>` (Storage RLS allows writes only in the owner's folder). Replaced and removed photos are deleted; covers that started sessions still use are kept when a club is deleted.
- Media paths start with the owner's account id (a Firebase UID, or a UUID in tests), which the media route accepts. Photos are served same-origin at `/api/media/<path>` (`routes/media.ts`), so no Supabase host is added to `img-src`. The bucket is public for reads and names carry random UUIDs, so responses are cached for good. Only upload paths get a large body (`isImageUpload`: the photo uploads, `PUT`, and adding a payment QR code, `POST .../payment-qrs`): `limits.uploadBodyBytes` in the API, and a matching `client_max_body_size 5m` location in `docker/proxy/nginx.conf` (the profile photo too). Anything else over `limits.bodyBytes` is refused with a plain message.
- Club rules (names, descriptions, limits, member tiers, plan validation) live in `server/src/utils/club/`; every change answers with the whole `ClubView`, so the page only renders it. `FEATURE_WEB_CLUBS` gates the API routes (`/api/clubs`, `/api/media`), the routes, the navigation item, and photo URLs (`coverUrl`/`avatarUrl` are `null` while it's off).

# Club Directory Requirements (Mandatory)
- Players find clubs on **Find clubs**, part of the club picker (`/choose-club`, `ClubFinder`; `/explore` redirects there; reached from the club switchers' menus and the site navigation): every club with a handle, newest first, `directoryLimits.pageSize` at a time ("Show more clubs"), searched by name or @handle (`GET /api/directory?q=&offset=`, the `security definer` function `club_directory`, which returns one row more than the page to say whether there's another). Each card (`DirectoryClubCard`, `.directory-card` in `.directory-card-grid`, at least 20rem wide) is a 4:3 rectangle (8:3 on phones, half as tall, its club and button in one row) without any border or frame, in Matchpoynt's colours, not the club's: filled edge to edge by the club's cover, or Matchpoynt's sidebar colour running into its accent. A soft blur covers the bottom half of the stage (`.directory-card-blur`: backdrop blur under a mask and a scrim, so white text reads on any photo) and another the top half (`.directory-card-blur-top`), framing it, and on it sit the club's photo, left-aligned beside its name, @handle and member count, then `JoinClubButton` as a full-width pill (primary "Join" whether the club joins at once or by request, "Member", "Request sent", "Accept invite" or "Manage club"). The rest of the card opens the club's page for players. The card has no coloured ring or edge: under a cover the stage is plain (`--deep`), the club's photo has no ring, and focus shows only for the keyboard, as a neutral outline.
- Opening a club (its pages in `ClubLayout`, or its page for players) shows `ClubLoadingScreen` until it has loaded: the club's photo, name and handle in its colours when lists loaded earlier already know them (`useClubPreview`, never fetching), skeletons in their place otherwise, and the logo's arches bobbing in turn (`arch-bob` keyframes, `motion.loops.archBob`). It's `aria-busy`, so tests wait for it.
- A club's page for players, `/c/<handle>` (`PlayerClubPage`, `GET /api/directory/:handle`, `club_player_page`), shows only what players need, never anything to edit: the club's info and social links with the join action (`JoinClubButton`); the welcome for members (`PlayerWelcomeCard`); sessions running now and planned (`PlayerSessionsCard`); badges to earn (`PlayerBadgesCard`, with `FEATURE_WEB_CLUB_BADGES`); the usual fee (`PlayerFeesCard`, with `FEATURE_WEB_FEES`); and the club leaderboard over its finished sessions (`PlayerLeaderboardCard`, ranked by the API's `clubStandings` in `server/src/utils/club/standings.ts`: wins, then win rate, then matches; names matched with `careerKey`). The page wears the club's colours.
- Joining: owners choose in settings (**Joining**, `ClubJoiningSettings`, `PUT /api/clubs/:id/joining`, `cleanJoining` in `server/src/utils/club/joining.ts`) whether people who ask join at once (`auto`) or wait for approval (`manual`, the default), plus a welcome message and up to `directoryLimits.welcomeLinks` links, shown only to members. `POST /api/directory/:handle/join` runs `request_join_club`: an open app invite links the caller to its member; `auto` adds them to the roster under their username with their tiers, linked to their account; otherwise it records a request (`club_join_requests`, one pending per person, with their tiers and photo as they were). Owners approve or decline on the Members page (`JoinRequestsCard`, `POST /api/clubs/:id/requests/:requestId`).
- Signing up for planned sessions: each plan picks how members get on its roster (`planned_sessions.sign_up`, `planSignUpModes`: `approval`, the default, where they ask and the owner approves; or `open`, where they sign themselves up) and an optional player cap (`max_players`), on the plan dialog's Details step (`PlanDetailsStep`; `maxPlayersProblem` refuses a cap below the roster). The rules are pure TypeScript in `server/src/utils/club/signUp.ts` (`signUpBlockedReason`, `spotsLeft`), sent on each plan's `PlayerSessionView` (`signUp`, `spotsLeft`, `signUpBlockedReason`). Members sign up or take themselves off ("Can't make it") in `PlayerSessionsCard` (`POST /api/directory/:handle/plans/:planId/sign-up`, `sign_up_for_plan`, 0050) and see who's coming (`PlanAttendeesDialog`, `GET .../attendees`, `plan_attendees`: names only, members and the owner). The reminder is in the app: Playing now's "Coming up" (`ComingUpCard`, `GET /api/play/upcoming`, `my_upcoming_plans`) lists the plans they're on that start within `signUpLimits.reminderWindowHours`. Emailed reminders aren't built: they need a scheduler (a cron calling the API), which neither delivery path has yet.
- Members ask to join a session from the club's page (`POST /api/directory/:handle/sessions`, `request_join_session`: members only, the plan or running session must be the club's and open). Owners decide on the Sessions page (`SessionRequestsCard`, `POST /api/clubs/:id/session-requests/:requestId`): approving adds them to a plan's roster, or to a running session through the engine's `addPlayer` (not checked in, so they check in at the venue).
- The club QR (`ClubQrButton` on the dashboard banner, with a handle) links to the join page `/join/<handle>` (`JoinClubPage`), laid out like a chat server's invite: the club's cover full-bleed, blurred and darkened (`.join-stage`), one centred card (`.join-card`) with the club's photo, name, handle and size (`GET /api/public/clubs/:handle`, `club_join_card`, readable signed out). Signed out, the card has the sign-in form with Google and a "Create account" tab with the sign-up form (`JoinSignedOut`), all returning to the join page; with profile details missing it shows the complete-profile form (`JoinProfileStep`); then it joins or asks (`JoinAction`) and shows the welcome.
- `FEATURE_WEB_CLUB_DIRECTORY` (default on; needs clubs and sign-in) gates `/api/directory`, `/api/public/clubs/:handle`, the join and session request routes, the Find clubs, club and join pages, their links, the Joining settings, the QR button and the request cards. `/api/people/search` needs clubs and sign-in.

# Player View Requirements (Mandatory)
- Players follow a running club session they're on from their own device, read only: **Playing now** (`/play`, `PlayPage`, a sidebar link in the **You** group) lists their clubs' running sessions with them on the roster (`GET /api/play`), and each opens `/play/<session id>` (`PlayerSessionPage`, `GET /api/play/:sessionId`), also reached from "Your place" on the club page's sessions.
- The view (`PlayerLiveView`, built by `playerLiveView` in `server/src/utils/session/playerView.ts` from the session's state, settled like the board's) shows: where they stand (`PlayerStatusCard`: the API's one-line `headline`, playing / placed / up next / queued / not checked in, how long they've waited, their place in the queue, matches before theirs, games and W–L), every court with who's on and for how long (`PlayerCourtsCard`), who plays next and against whom (`PlayerUpNextCard`, automatic queueing: `upcomingMatches`, so it's exactly what starting a court picks; a match is "up next" when it's within the free courts), and the queue in call order with waits (`PlayerQueueCard`). Their own court, match and row stand out (`.play-mine`). Only names, never contacts or tiers.
- The viewer is matched to the session roster by their name on the club's roster (`careerKey`). Sessions are the owner's under RLS, so they're read through the `security definer` functions `player_live_session` (members of the session's club and its owner, running sessions only, without link codes) and `player_live_sessions`.
- While they're on court, the status card gives way to "You are now playing" (`NowPlayingBanner`, with the leaderboard badges they hold in this session, `badges`/`streak` on `PlayerLiveMe`, `.play-now`: about 40vh tall, everything centred): the court, the match clock and the two sides with "vs" between, in the board's own layout (`.court-matchup`, `.court-side`), their side labelled "Your side" and the other "Opponent side" (`mySide` on `PlayerLiveCourt`, from the API).
- The page has three tabs: **Your session** (their status or "You are now playing", the courts and up next), **Queue** (`PlayerQueueCard`, only its rows scroll: `.play-queue-scroll` caps ScrollArea's viewport) and **Leaderboard** (`PlayerLeaderboard`: the board's `LeaderboardBoard`, from `GET /api/play/:sessionId/leaderboard`). Both the board's leaderboard and this one are built by `leaderboardView` (`server/src/utils/session/leaderboardView.ts`); the players' one leaves out the club's own badges, which only the owner can read.
- Their badges show on the status card and "You are now playing" (`PlayerBadges`): the club's own (`clubBadges` on the view and `PlayerLiveMe`, awarded by `awardClubBadges` with career totals over the club's finished sessions and this one; `player_live_session` returns the club's badges and history, 0038) before Matchpoynt's. Under the current state, after a divider, the session's **Match history** (`history`, every finished match newest first, in `RecentMatches`).
- When the session ends, the page turns into its ended screen by itself (`GET /api/play/:sessionId` answers `PlayerSessionEndedView`, `ended: true`, through `player_ended_session`; polling stops): "Session ended", the club's feedback form for it inline (`FeedbackAnswerForm`, or thanks once sent), and its **Final leaderboard** (the players' leaderboard endpoint answers for ended sessions too).
- Motion (`animations/playMotion.ts`, GSAP, skipped under reduced motion): each tab's content rises in as it opens and its figures count up (`PlayReveal`, `playEntrance`, `[data-play-reveal]`, `[data-play-row]`, `[data-count]`); queue rows slide to their new places as it refreshes (`useLiveRows`, Flip, climbers highlighted like the leaderboard's); "You are now playing" pops in with the two sides sliding in from either side and "vs" landing between (`nowPlayingEntrance`); going on or off court, the card hands over to the next (`PlayStatusSwap`, `swapStatus`: the old card, as last drawn, lifts away while the new one rises and the space resizes). Timings are `motion.gsap.play`.
- What a player checks most, all worked out by the API (`playerView.ts`) and shown on the status card (`PlayerStatusCard`):
  - **Checking in from the app**: while they're on the roster but not checked in (`canCheckIn`), "I'm here: check me in" (`usePlayerCheckIn`, `POST /api/play/:sessionId/check-in`) runs `player_check_in` (security definer, 0039): the caller's name on the club's roster finds their session player, and only `checked_in_at` is recorded, as the venue's QR does (no version bump; `settleCheckIns` queues them). It answers with the refreshed view.
  - **Their next match up front** (`nextMatch`, `PlayerNextMatch`: their partners and opponents from `upcomingMatches`) and **when it should start** (`estimatedStartAt`, `estimatedStart` in `server/src/utils/session/waitEstimate.ts`: the open-play courts free now or once their match has run the session's typical length, `typicalMatchMs`: the median of its latest finished matches, else the time limit, else `playerViewConfig.defaultMatchMinutes`; matches take the earliest free court in turn). Shown as "Starts in about 12 min" (`formatStartsIn`).
  - Their **place on the leaderboard** (`rank` of `ranked`, once they've played), **points for and against**, and the **fee so far** while the session charges one (`fee`: `amountFor` over their games, with `invoiceBreakdown`).
  - **About this session** (`PlayerSessionInfoCard`, `info`: format, time limit, courts, how long matches take, how the queue works, the fee) and **Friends here** (`PlayerFriendsHereCard`, `friendsHere`: their friends on the roster, matched by username, and whether each is on court, waiting or not checked in; the route passes the friends while `FEATURE_WEB_FRIENDS` is on).
  - **Alert me when I'm called** (`CalledAlertButton`, `useCalledAlert`, remembered in this browser, `calledAlert` in `remember.ts`): moving to up next or onto a court buzzes the phone (`navigator.vibrate`, `play.calledVibration`), shows a system notification while the page is in the background (permission asked once; `utils/platform/calledAlert.ts`) and toasts. The status is the API's; wording is `play.called` in `config/play.ts`.

# Fee and Invoice Requirements (Mandatory)
- A session can charge a joining fee (`fee` on `SessionSettings`, `FeeScheme` in `shared/src/interfaces/Fee.ts`), set on the last setup step, **Fees** (`FeesStep`, also in Session settings and `PlanSessionDialog`): no fee, **fixed** (everyone pays `base`), **per game** (`perGame` × games played) or **base price + per game**. Amounts are whole minor units (cents) in one of `feeCurrencies` (`shared/src/config/fees.ts`); the form (`FeeSchemeFields`, `AmountField`) only turns what's typed into minor units (`utils/forms/money.ts`).
- A club saves its own fee scheme in its settings' Fees group (`ClubFeeSettings`, `PUT /api/clubs/:id/fee`, column `clubs.fee`), or while being created. `ClubSummary` carries `fee` and the API's `feeSummary`. The Fees step offers every club's saved fee ("Use <club>'s fee"), and a new planned session starts with its club's fee (`planned_sessions.fee`, carried into the session by `planToSetup`). The fee is copied, never linked: changing the club's scheme never changes a session or its invoices.
- The rules are pure TypeScript in `server/src/utils/fees/`: `rules.ts` (`validateFee`, `cleanFee`, `keptFee`, `amountFor`, `feeSummary`, `invoiceBreakdown`, `formatMoney`) and `invoices.ts` (`sessionInvoices`, `invoiceGroup`). Setup validation reports fee problems on the `fees` step.
- A fee can ask for a **downpayment** (`downpayment` on `FeeScheme`, minor units; 0 or left out for none; less than a fixed fee, no more than a base price; `validateFee`, `downpaymentText`): what players may pay first. It's a field of `FeeSchemeFields` ("Downpayment (optional)").
- **Payments** are recorded in parts, each cash or online (`InvoicePayment`: `id`, `amount`, `method` (`cash` | `online`, `null` for those from before), `paidAt`; stored as the `payments` JSON list on `session_invoices` and `club_invoice_payers`, with `paid_at` the day it was paid in full; 0040/0041, which made earlier paid invoices one payment without a method). The rules are pure TypeScript in `server/src/utils/fees/payments.ts`: `paymentState` (paid, left, `status`: `paid` | `partial` | `unpaid`), `withPayment` (refuses nothing, more than what's left, or anything once paid), `withoutPayment`, `markedPaid` (the rest as one payment by a method; unpaid clears them), `paymentTotals` (a group's paid counts partial payments; `paidCount`, `partialCount`). Routes: `PUT .../:invoiceId` (`{ paid, method }`), `POST .../:invoiceId/payments` (`{ amount, method }`), `DELETE .../:invoiceId/payments/:paymentId`, for sessions under `/api/invoices/:sessionId` and manual payers under `/api/accounting/:clubId/invoices/:invoiceId/payers/:payerId`; each answers with the group. `InvoiceGroupCard` keeps the paid tick (paid in full, recorded as "Mark paid as" cash or online, `PaymentMethodPicker`), shows each row's `PaymentStatusBadge`, and each row's payments dialog (`InvoicePaymentsDialog`: the payments with their method, removable; recording one, the downpayment first when the fee asks for one, else what's left). The accounting dashboard counts each payment as collected on its own day.
- Clubs keep **payment QR codes** (`clubs.payment_qrs`, [{ id, label, path }], up to `paymentQrLimits.maxQrs`; `server/src/utils/club/paymentQrs.ts`): added and removed in the club settings' **Payment QR codes** group (`ClubPaymentQrSettings`; `POST /api/clubs/:id/payment-qrs` multipart with `image`, `label` and `position`, `DELETE /api/clubs/:id/payment-qrs/:qrId`), and framed like the club's photos: the picked image opens in `PhotoAligner` (shape `square`, its button "Upload QR code") before uploading, and "Adjust framing" reframes one later (`PUT /api/clubs/:id/payment-qrs/:qrId/position`, `uploadedQrPosition`, `cleanPosition`); everywhere a QR code shows it's drawn at its framing (`PositionedPhoto` in `.qr-frame`), stored in `club-media` as lossless WebP (`toWebp(..., { lossless: true })`, path kind `qr`) so they still scan, and sent as `paymentQrs` on `ClubSummary`. Members see them on a session's ended page (below).
- Finishing a session writes its invoices: `POST /api/sessions/:id/end` passes `sessionInvoices` to `end_session(p_session_id, p_expected_version, p_invoices)`, which ends the session and inserts them into `session_invoices` in one transaction (0024). Everyone who came (checked in and still on the roster) or played at least one game is invoiced, by name; nobody is invoiced for 0 (a per-game fee with no games). After that, invoices are only marked paid or unpaid.
- The finished session's page shows its invoices above the leaderboard (`SessionInvoices`, `InvoiceGroupCard`, only when `EndedSessionView.hasFee`): the fee, collected of total, what's still owed, and a row per player with a "paid" checkbox (`PUT /api/invoices/:sessionId/:invoiceId`, body `{ paid }`, answering with the group and its new totals). Marking an already-paid invoice paid keeps its date.
- There is no separate Session invoices page: a session's invoices are on its own page (above), and a club's (sessions' and manual) on the club's Invoices page. Old `/app/invoices` links redirect to `/app`. The API still computes every total (`total`, `paid`, `outstanding`, `paidCount`) and every sentence (`summary`, `breakdown`).
- An invoice group (`InvoiceGroupView`) is either a session's invoices (`kind: 'session'`) or a manual invoice (`kind: 'manual'`, see Club Accounting Requirements); both show in `InvoiceGroupCard`, and `useMarkInvoicePaid` picks the route by kind.
- Toggle: `FEATURE_WEB_FEES` (default on) gates the Fees step, the club fee card and its route, the invoice routes (`/api/invoices/:sessionId`) and the invoices on a finished session's page. While it's off, sessions load with `fee: null`, saves leave a stored fee alone (`save_session` only touches `fee` when the save carries the key, like `tournament`), plans keep theirs, and ending a session writes no invoices.

# Club Accounting Requirements (Mandatory)
- Each club has four more pages, each a sidebar link in the club's group: **Invoices** (`/clubs/<id>/invoices`, `ClubInvoicesPanel`: a list, `InvoiceList`, each row opening the invoice's own page, `/clubs/<id>/invoices/<manual|session>/<id>`, `ClubInvoicePage`, with the full `InvoiceGroupCard`, payments and deleting a manual invoice; `GET /api/accounting/:clubId/invoices/:invoiceId` or `GET /api/invoices/:sessionId`), **Expenses** (`/expenses`, `ExpensesPanel`: a list, `ExpenseTable`, each row opening the expense's own page, `/clubs/<id>/expenses/<id>`, `ClubExpensePage`, `ExpenseDetails`, where it's edited and deleted; `GET /api/accounting/:clubId/expenses/:expenseId`), **Billers** (`/billers`, `BillersPanel`) and **Accounting** (`/accounting`, `AccountingPanel`).
- **Manual invoices** (`club_invoices`, `club_invoice_payers`): invoices a club makes outside sessions (`ManualInvoiceDialog`): what it's for, notes, the day issued, a currency and an amount that is either what **each** payer owes or a **total** split evenly between them (`payerAmounts`: leftover cents one each to the first payers), and its payers: club members ticked from the roster or anyone else by name (`PayerPicker`). `cleanManualInvoice` (`server/src/utils/accounting/invoices.ts`) checks it and names members as on the roster; `create_club_invoice` (security invoker, 0028) writes the invoice and its payers in one transaction. Each payer has a paid tick (`PUT /invoices/:invoiceId/payers/:payerId`, answering with the invoice and its totals, `manualGroup`); invoices can be deleted (`DELETE /invoices/:invoiceId`). The club's Invoices page (`GET /invoices?from&to&tz`) lists its manual invoices and its sessions' invoices for the period, newest first. Manual invoices count in the dashboard: invoiced on the day issued, collected on the day each payer was ticked. Their API is `routes/accounting.ts`, mounted at `/api/accounting/:clubId/...`; the club must be the caller's, and RLS checks every row.
- **Billers** (`club_billers`): who the club pays, with a name (unique in the club, any case), optional contact and notes (`BillerDialog`; `GET/POST /billers`, `PUT/DELETE /billers/:billerId`, each answering with the list and each biller's expense count). Deleting one keeps its expenses, with no biller.
- **Expenses** (`club_expenses`): a description, an amount above zero in minor units of one of `feeCurrencies`, the day it was spent, an optional biller, optional notes, and either the whole club (global) or one of the club's sessions (`ExpenseDialog`, "Applies to"). The API refuses a biller or session that isn't the club's (`cleanExpense`). The list (`GET /expenses?from&to&biller&scope`, `scope` = `global`, `session` or a session id) is newest first, up to `accountingLimits.listLimit`, with totals per currency (`moneyTotals`). Deleting the session keeps its expenses as club-wide.
- **Accounting** (`GET /summary?from&to&tz`): `accountingSummary` in `server/src/utils/accounting/summary.ts`, from `loadLedger` (the club's finished sessions, their invoices while fees are on, and its expenses and billers). Cash basis: **collected** counts on the day an invoice was marked paid, **spent** on the day an expense was spent, and **net earnings** = collected − spent; **invoiced** and **still owed** count on the day the session ended. It answers per currency (busiest first): totals, every month in the range (empty ones too, up to `accountingLimits.maxMonths`), each session's invoices less its own expenses, club-wide spending, and spending by biller. Days and months are counted in the viewer's time zone (`tz`, the browser's IANA zone, checked by `cleanTimeZone`).
- The dashboard shows four tiles (`AccountingTile`: net earnings, collected, spent, still owed), a monthly chart of collected and spent (`MonthlyChart`: thin paired bars on one axis, a legend, a tooltip on hover and focus with the month's net; colours are the `chart-collected`/`chart-spent` theme tokens, validated as a colour-blind-safe pair) with the same figures as a table (`MonthlyTable`), a per-session table (`SessionProfitTable`) and spending by biller (`BillerSpendList`).
- Dates: `DateRangeFilter` offers presets (this month, last month, last 3 months, this year (the default), last 12 months, all time) or custom days (`utils/forms/dateRange.ts`). The choice lives in the address (`?period=`, plus `from`/`to` for custom dates, `useDateRange`) and carries over between the Expenses and Accounting tabs. The API checks the range (`cleanRange`: real days, not backwards, at most five years).
- The rules are pure TypeScript in `server/src/utils/accounting/` (`rules.ts`, `summary.ts`), tested in `test/unit/api/utils/accounting/`. `e2e/club/accounting.spec.ts` covers billers, expenses and the dashboard against `FakeAccounting` (`e2e/support/fakeAccounting.ts`, the same rules in memory).
- Toggle: `FEATURE_WEB_ACCOUNTING` (default on; needs clubs) gates the routes, the three tabs and their sidebar links. With fees off, the dashboard counts expenses only.

# Tournament Requirements (Mandatory)
- Every court card has a "Tournament" switch (`CourtTournamentSwitch`). Switching the first court on opens `TournamentSetupDialog`, where the Queue Master picks:
  - **format:** single elimination, double elimination (losers bracket, grand final, and a reset final when the losers-bracket side wins it), round robin, or pools then knockout (pool count and how many go through);
  - **entrants:** in singles every player is an entrant; with more per side, fixed teams (balanced by tier, random draw, or picked by hand in `TeamPicker`) or rotating partners (round robin only: new partners every round, players ranked one by one);
  - the checked-in players taking part, and seeding (by tier or random).
  More courts join or leave with their switch (`PUT /api/sessions/:id/courts/:courtId/tournament`); a court with a match on can't switch.
- While a tournament runs, the queue panel lists who's competing as checkboxes (`TournamentCompetitors`: competitors ticked, waiting players unticked). Ticks only shape the selection (in doubles players join in pairs); "Update tournament" sends the whole list (`PUT /api/sessions/:id/tournament/competitors`) and the API redraws the bracket with the same settings (`setTournamentCompetitors` in `tournament/setup.ts`, using the setup stored on the tournament). Competitors sit out open play, which is how matchmaking knows who they are. It locks with the API's reason (`competitorsBlockedReason` on the view) once a tournament match has been played, or when teams were picked by hand.
- Tournament courts play bracket matches only; other courts keep open play. Players still in the tournament are held out of the open-play queue, lineups and roster removal until they're knocked out or it finishes (`heldPlayers`). Each open tournament court previews the exact match it starts next (`courtAssignments`), and auto-fill starts tournament matches whenever auto-fill is on, whatever the queueing mode. A tournament match must finish with a score.
- While a tournament exists, the session page has a Tournament tab (`TournamentPanel`): progress, publish and cancel, then `TournamentBoard` (champion, on court now, up next with Start buttons, brackets drawn as columns with connector lines, pool tables and rounds). Cancelling (or closing a finished one) returns its courts and players to open play; played matches stay on the leaderboard.
- The rules are pure TypeScript in `server/src/utils/tournament/`: `bracket.ts` (generation), `progress.ts` (byes and walkovers, results moving on, reset final, pools into knockout, standings, eliminations, champion), `teams.ts`, `play.ts` (tournament matches on courts), `setup.ts` (create, court switch, start, cancel) and `view.ts` (every label, such as "Quarterfinal 2" or "Winner of Semifinal 1"). The session engine calls into them. Draws use `EngineContext.random`, so tests are repeatable.
- The tournament is saved as one JSON document on the session (`sessions.tournament`) with each court's flag (`session_courts.tournament`), by `save_session`, so it shares the session's version. `save_session` only touches them when the save carries a `tournament` key: with `FEATURE_WEB_TOURNAMENTS=false` the API loads sessions without tournaments (courts play open play) and never erases one.
- Publishing gives an unguessable `/t/<slug>` link (`sessions.tournament_slug`; `POST`/`DELETE /api/sessions/:id/tournament/publish`). `PublicTournamentPage` reads `GET /api/public/tournaments/:slug` through the `security definer` function `public_tournament`, refreshes on its own and toasts new results. `FEATURE_WEB_TOURNAMENTS` gates the switch, tab and API; `FEATURE_WEB_PUBLISH_TOURNAMENTS` gates the publish button, the public route and endpoint.

# Local Cache Requirements (Mandatory)
- Non-sensitive club and profile details are kept on the device so pages open without waiting: TanStack Query's persister (`PersistQueryClientProvider` in `App`, `utils/api/persistCache.ts`, settings in `config/cache.ts`) writes a whitelist of query results to localStorage (`matchpoynt.cache`). Kept: `me` with the email taken out, your first page of clubs (`['clubs']`, club summaries), clubs' pages for players and join cards. Never kept: config and toggles (they fail closed), sessions, the owner's full club view (members and contacts), invoices, money, profile details beyond name, username and photo.
- The kept club details count as fresh for `localCache.clubStaleMs` (5 min), so they aren't fetched again on every page; changes made in the app invalidate them at once. `me` is always checked again, but draws the sidebar straight away.
- A new app version (`buster`), signing out (`useSignOut` clears the query client) or a different account signing in (`forgetOnAccountChange`) drops what was kept. With storage blocked nothing is kept.
- Further options, not built: HTTP revalidation (the API sending `ETag`/`Cache-Control: private` on club and profile reads so unchanged data answers 304), and on desktop keeping the same whitelist in the Rust side's SQLite store with the offline engine.

# API Requirements (Mandatory)
- The API is Hono on Node in `server/`, mounted at `/api`. Routes live in `server/src/routes/`, one file per area (`auth.ts`, `sessions.ts`, `public.ts`, `config.ts`).
- Business logic is pure TypeScript in `server/src/utils/session/` (engine, matchmaking, scoring, setup, leaderboard, view). It takes state and an injected `EngineContext` (clock and id source) and returns new state, with no I/O. Every rule has Vitest tests in `test/unit/api/`, at the same path as the code (`server/src/utils/session/engine.ts` → `test/unit/api/utils/session/engine.test.ts`). Run them with `pnpm test:unit`.
- A request is handled in this order: Zod shape check (`utils/validation/schemas.ts`), load state (`queries/`), apply the engine, save, then return a view built by `utils/session/view.ts`.
- Rule violations throw `ApiError` (`invalid`, `conflict`, `not_found`, `unavailable`, …). Its message is written for the user and may carry `fields`. Zod failures name each bad field. Database and Auth failures are mapped to specific messages in `utils/supabase/errors.ts`, e.g. a missing migration, RLS denial, Supabase unreachable, or Supabase not trusting Firebase tokens. Firebase Auth failures are mapped in `utils/firebase/errors.ts` (`authFailure`), e.g. a provider turned off, a weak password or an expired link. Every response carries an `X-Request-Id`, and error bodies repeat it as `requestId`. Server-side logs include it, so a user's banner reference finds the log line. Unexpected errors become a 500 without details and are logged server-side only.
- The API never trusts client ids. Unknown court or player ids in a setup get fresh server UUIDs.
- Concurrency is optimistic. Every session change sends `If-Match: <version>`, and a stale version answers 409 so the client refetches.
- CSRF protection: state-changing requests must carry an `Origin` matching `APP_URL` (or `Sec-Fetch-Site: same-origin`), on top of `SameSite=Lax` cookies.
- Public, signed-out endpoints live under `/api/public/` and read only through narrowly scoped `security definer` functions (e.g. `public_leaderboard`). Published links use unguessable 128-bit slugs.
- `server/src/config/env.ts` validates required variables with Zod at startup and names any that are missing.
- The production build bundles the API, including `shared/` and all dependencies, with esbuild, so nothing at runtime needs `node_modules`: `dist/index.js` (the Node server, `src/index.ts`, for Docker) and `dist/vercel/index.js` (the Vercel Function, `src/vercel.ts`, which default-exports the app). Both run `checkStartup` (`config/startup.ts`) first. Native modules are therefore out: photo conversion uses jSquash's WebAssembly codecs, whose `.wasm` files the build copies to `dist/wasm` and `dist/vercel/wasm` (found next to the bundle in production, in `node_modules` in development). The bundle's `require` banner aliases `createRequire`, so source files may import it too.

# Backend Requirements (Supabase + Drizzle) (Mandatory)
- Supabase provides Postgres and Storage; Firebase provides Auth. Only the API talks to either.
- Supabase trusts Firebase through Third-party Auth (Authentication > Third-party Auth > Firebase, with the Firebase project id). An account id is the Firebase UID, the token's `sub`: owner columns are `text`, RLS compares them with `(select auth.jwt() ->> 'sub')` (`authUid` in `schema.ts`), and nothing references `auth.users`. Never use `auth.uid()`: it casts `sub` to uuid and fails for a Firebase UID.
- The API uses only the publishable (anon) key and runs each query as the signed-in user by sending their Firebase ID token as the access token (`supabaseAs` in `server/src/utils/supabase/client.ts`). RLS therefore applies to every request. The Supabase service-role key is not used anywhere: not in `server/`, not in a container, not in CI. The Firebase service account is used only by the API, only to grant the `role` claim and look up whether an email has an account.
- Signed-out reads (published leaderboards) use an anon client (`utils/supabase/anon.ts`) that can only call functions granted to `anon`.
- The schema lives in code in `server/src/db/schema.ts` (Drizzle `pgTable`, with `pgPolicy` and the `drizzle-orm/supabase` roles and helpers). Never change the schema from the Supabase dashboard.
- Migrations are generated, never hand-edited:
  - `pnpm db:generate` writes the next migration to `server/drizzle/` from the schema.
  - SQL the schema can't express (functions, grants) goes in a custom migration created with `pnpm --filter @matchpoynt/server db:migration <name>`.
  - `pnpm db:migrate` applies migrations using `DATABASE_URL`, which only migrations ever use.
  - CI fails if the schema changed without a migration.
- Row Level Security is on for every table, with policies defined next to the table in `schema.ts`. Authorization relies on RLS and API checks, never on hiding UI.
- Multi-table writes go through Postgres functions (`save_session`, `end_session`) so they happen in one transaction, with a version check. These functions are `security invoker`, so RLS still applies.
- `server/src/types/database.ts` types the supabase-js client. Regenerate it with `pnpm --filter @matchpoynt/server db:types` after migrating, and keep it in step with `schema.ts`.
- Every sport-scoped table queried across sessions (sessions, matches, rankings, seasons, fees, player tiers) has a `sport_id` column that matches a key in `shared/src/config/sports.ts`.

# Shared Package Requirements (Mandatory)
- `shared/` (`@matchpoynt/shared`) holds data and types used by both the web app and the API: sport rules, session defaults, feature defaults and env names, and request/response interfaces. It contains no logic and no React. A data constructor is fine; a rule is not.
- `shared/` is consumed as TypeScript source by Vite, tsx and esbuild. It has no build step.

# Multi-sport Requirements (Mandatory)
- Never hard-code a sport. Each sport's name, scoring formats (points to win, cap/deuce rules, singles/doubles), skill tiers and terminology live in `shared/src/config/sports.ts`, typed by `SportRules`.
- Racing to a ceiling is its own scoring choice, apart from the 21-point formats (which keep their standard cap of 30): "Race to the ceiling" is a group of formats (`raceTo` in `shared/src/config/sports.ts`, ids `race-<n>` for 30, 31 and 35), each one game where the first side to the ceiling wins with no deuce (`pointsToWin` = `cap` = n, `winBy` 1). Each has `group`, `groupDescription` and `variant` ("Race to 31"); the Scoring step lists the group as one entry with its variants side by side (`ScoringStep`), and a session picks one like any format.
- UI copy uses sport-neutral words: court, match, game, player, session, queue. Sport-specific labels (e.g. "shuttle fee", "ball fee") come from the sport config.
- Sessions, rankings, seasons and fees are scoped per sport. A player can hold a different tier in each sport. A session is for one sport and cannot switch.

# Desktop App Requirements (Mandatory)
- The desktop app is Tauri v2 wrapping the same Vite build, with the Rust side in `src-tauri/`. Do not fork the UI for desktop: there is one `src/`. Platform differences sit behind `utils/platform/` (`isDesktop()`), and desktop features are toggled by `FEATURE_DESKTOP_*` through `/api/config`.
- Rust commands live in `src-tauri/src/commands/`, one file per concern (e.g. `storage.rs`, `updates.rs`), and are registered in `lib.rs`. Each command is declared in `build.rs` (`AppManifest`) so it is denied by default and granted explicitly in `src-tauri/capabilities/`. The frontend calls them only through typed wrappers in `utils/desktop/`, never `invoke()` directly from a component.
- Least privilege: grant only the Tauri permissions the app actually uses, in `src-tauri/capabilities/`. No wildcard filesystem, shell or HTTP scopes. Keep a strict CSP in `tauri.conf.json` and never load remote scripts into the webview.
- The desktop app calls the Matchpoynt API (never Supabase) through `@tauri-apps/plugin-http`, with its URL scope limited to the API's origin. This is the desktop counterpart of the nginx proxy rule. `utils/api/client.ts` gets the plugin's `fetch` through an adapter, so the same hooks run on both targets.
- Sign-in on desktop opens the system browser (`@tauri-apps/plugin-opener`) at the API's sign-in route and returns through a deep link (`@tauri-apps/plugin-deep-link`) carrying a one-time code. A Rust command exchanges the code with the API for a session token and stores it in the OS keychain. The webview never sees the token; Rust attaches it to API requests. Never run third-party sign-in inside the webview.
- The desktop app must work offline for Queue Masters, and the Rust side counts as server side. When offline:
  - The webview calls Rust commands instead of the API, and Rust runs an offline engine (`src-tauri/src/offline/`) that implements the same session rules as `server/src/utils/session/`.
  - Data goes to SQLite through Rust inside the app's data directory, and changes are queued with the session version.
  - Back online, Rust replays the queue to the API. The API's version check decides conflicts, and the server's state wins.
  - The webview runs no rules in either mode.
  - The Rust engine is tested against the same cases as the TypeScript engine. When a rule changes in one, change it in the other in the same commit.
- No secrets in the desktop bundle, because shipped binaries can be inspected. Per-user tokens go in the OS keychain behind a Rust command. Signing secrets (updater key, Apple and Windows code signing) exist only as CI secrets, never in the repo or in a committed `.env`.
- Updates ship through `@tauri-apps/plugin-updater` with signed artifacts. The updater public key lives in `tauri.conf.json`; the private key exists only in CI.
- One source of truth for identity. App name and version come from `package.json` and `config/site.ts`, and `tauri.conf.json` reads its version from `package.json`. The bundle identifier is reverse-domain and must not end in `.app` (e.g. `com.matchpoynt.desktop`). Icons are generated with `pnpm desktop:icons` from one source image (`public/favicon.svg`).
- Desktop builds run in CI on a macOS, Windows and Linux matrix with `pnpm tauri build`, not in Docker. Docker and Docker Compose remain the web and API delivery path only.
- Keep Vite compatible with `pnpm tauri dev`: fixed port with `strictPort`, `clearScreen: false`, and `TAURI_ENV_*` in `envPrefix`.
- git ignore `src-tauri/target/` and `src-tauri/gen/schemas/`; docker ignore all of `src-tauri/`.
- Rust code is formatted with `cargo fmt` and linted with `cargo clippy -- -D warnings`, and every command has unit tests (`cargo test`).
